## Goal

Inventory approved source files without parsing them into business tables.

## Scope

Implement only this task. Do not begin dependent tasks implicitly.

## Acceptance criteria

- [x] Each file has source, size, checksum, and collection timestamp
- [x] Repeated runs are idempotent
- [x] Invalid paths fail safely

## Evidence

### Changed files

- `src/boat_prediction/inventory.py` (new): `build_inventory()` walks an
  approved raw directory, computes SHA-256 + size per file, and
  upserts a JSON manifest (`data/manifests/source_inventory.json` by
  default) keyed by relative path.
- `tests/test_inventory.py` (new): 7 tests covering recording, suffix
  filtering, idempotent re-run, changed-file re-collection, historical
  retention of removed files, and safe failure on a missing directory /
  corrupt manifest.

### Commands and tests

- `python -m unittest discover -s tests -p 'test_*.py'` — 14 passed
- Manual smoke test: `python -m boat_prediction.inventory <dir> --source official --manifest <path>` against a temp dir with one `.txt` and one `.md` file — only the `.txt` file was inventoried; re-run kept the same `collected_at`; pointing at a nonexistent directory exited 1 with a clear message (no traceback).
- `python scripts/quality_gate.py` — passed

### Decisions and risks

- Default approved suffixes: `.lzh, .txt, .csv, .zip, .json` (official
  boatrace downloads are typically `.lzh`/`.txt`; `.csv`/`.json` cover
  admin uploads per `docs/domain/.../implementation_guide.md` §6.1).
  Caller can override via `allowed_suffixes`.
  **Risk:** this list is a reasonable guess, not sourced from a
  confirmed `data_sources` registry (that table doesn't exist yet).
  Revisit once real source files / P0-T004 ingestion define exact
  formats.
  - **Rejected alternative — file mtime as `collected_at`:** would be
  fully stateless, but drifts from the guide's definition (`collected_at`
  = "this system's" acquisition time, distinct from the file's own
  timestamp) and can be altered by copy/checkout operations. Chose a
  persisted manifest with checksum-based upsert instead, matching the
  guide's idempotency pattern (§9.2: dedupe by content hash).
- Manifest keeps entries for files later deleted from `raw_dir` as a
  historical audit trail (no destructive update of past records) — flagged
  here since it means the manifest is append/upsert-only, not a mirror of
  current disk state.
- No business-table parsing, DB writes, or network calls were added, per
  scope.
