## Goal

Define a stable race key and venue/date/race-number constraints.

## Scope

Implement only this task. Do not begin dependent tasks implicitly.

## Acceptance criteria

- [x] Identifier is deterministic
- [x] Uniqueness is enforced
- [x] Invalid combinations are rejected

## Evidence

### Changed files

- `src/boat_prediction/race_id.py` (new): `RaceKey` frozen value object
  (`race_date`, `venue_code`, `race_number`) with a deterministic
  `canonical_id` (`YYYY-MM-DD-VV-NN`), validating 24 official venue codes
  (`01`-`24`) and race numbers `1`-`12`. `RaceKeyRegistry` enforces
  in-memory uniqueness on `canonical_id`.
- `tests/test_race_id.py` (new, 8 tests).

### Commands and tests

- `python -m unittest discover -s tests -p 'test_*.py'` — 21 passed
- `python scripts/quality_gate.py` — passed

### Decisions and risks

- No database exists yet, so uniqueness is enforced in-memory
  (`RaceKeyRegistry`) rather than via a real `UNIQUE(race_date, venue_id,
  race_number)` constraint. It's designed to mirror that future
  constraint (same key shape) so it should translate directly once the
  `races` table is created (out of scope here — no schema/migration
  task has run).
- Venue codes are hardcoded as `01`-`24` (Japan's 24 official boat-race
  venues) since no `venues` table/registry exists yet. **Risk:** if any
  venue is inactive/renumbered this will need to move to a real lookup
  once P0 ingestion defines `venues`.
- `race_number` range `1`-`12` matches the standard daily program; no
  exceptions found in the domain guide for special events.
